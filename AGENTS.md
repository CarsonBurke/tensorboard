# Local TensorBoard Notes

- Always build with `-c opt`. `bazel-bin` is a symlink to the last build's configuration, so a plain (fastbuild) build silently swaps the launcher onto debug binaries: the debug Rust data server is 4-9x slower per RPC.
- When TensorBoard runtime changes should affect the repo-local TensorBoard binary, rebuild `bazel-bin/tensorboard/tensorboard` with `npx -y @bazel/bazelisk build -c opt //tensorboard:tensorboard`.
- Data-server reload pokes need `npx -y @bazel/bazelisk build -c opt //tensorboard/data/server:server`. The launcher sets `TENSORBOARD_DATA_SERVER_BINARY` to that binary.
- `/home/marvin/.local/bin/tensorboard` launches the repo-built binary. Existing TensorBoard processes must be restarted to pick up Python, UI, or data-server changes.
- Never set `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`. The runfiles ship a native protobuf backend (`cpp` in opt builds, `upb` otherwise) and the default picks it; the pure-Python decoder made a 4.8 MB metadata listing take 4-5 s instead of 0.3 s.
- Both the refresh button and the auto-reload timer hit `GET /data/reload`, which rescans the logdir before refetching runs, so new runs appear without restarting the server. Auto reload is off by default (`reloadEnabled: false`); enable it in the settings panel or seed `_tb_global_settings` with `{"autoReload": true, "autoReloadPeriodInMs": 16000}` in localStorage when testing it.
- Bazel's own resource policy lives in `~/.bazelrc`, not this repo: the server idles out after 15 minutes (default is 3 hours), the JVM is capped at 3 GiB, and each worker mnemonic gets 2 instances instead of 4. Without it, a TypeScript build left ~8 `tsc_wrapped` Node workers of 600-800 MB resident for the rest of the day. Build times are unchanged (21 s either way for an incremental `//tensorboard/webapp:karma_test` after touching a file with 362 importers); peak worker memory is 3.3 GiB instead of 5.4 GiB. `npx -y @bazel/bazelisk shutdown` reclaims it immediately.
